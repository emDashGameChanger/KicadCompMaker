??? note "Architecture"
    - `plugin.py` — entry point / `DigikeyPlugin` (the `ActionPlugin`). Owns credential handling (`get_token`, `_ensure_credentials`), one generic search path (`_start_search` → `_api_worker` on a worker thread → `_on_api_result` shows `ResultDialog` with a per-tab processor/generator), `_save_state` (saves every control registered in the dialog's `radio_groups`/`text_fields`), the transistor pinout gate (`_confirm_and_generate_transistor`, `_confirm_pinout`), and `generate_library_files`, which writes/appends the generated symbol + footprint into the shared per-category libraries under `~/.local/share/kicad/9.0/{symbols,footprints}/`.
    - `gui.py` — all `wx` dialogs: `DigikeyDialog` (main tabbed search form), `ResultDialog` / `BatchResultDialog` (results + report), `CredentialsDialog`, `JsonViewDialog`, `ProgressCounterDialog`.
    - `TH_Resistors.py`, `TH_Radial_ElectrolyticCapacitors.py`, `TH_Disc_Capacitors.py` — one module per component type. Each exposes a `search_tht_*` (Digikey product search) and `process_*`/`process_disc_capacitor` (turns a chosen product JSON into symbol/footprint data, including procedurally generating footprint polygons for the electrolytic can silkscreen in `generate_capacitor_polygons`).
    - `TH_Diodes.py`, `TH_Transistors_{BJT,JFET,MOSFET}.py` + `TH_Transistor_Common.py` — despite the `TH_` prefix these serve both mounts via `smd=` / `lib_config={'smd': True}`; `TH_Transistor_Common` holds the THT and SMD package→stock-footprint tables, `build_pinout_confirm` and `apply_pinout`.
    - `SMD_Common.py` — SMD stock-footprint tables and pickers (`chip_footprint`, `tantalum_footprint`, `alum_footprint`), Digi-Key package ValueIds, `search_leaf`. `SMD_Resistors.py` / `SMD_Capacitors.py` — `search_smd_*` + `process_smd_*` (MLCC, tantalum, aluminium).
    - `Stock_Parts.py` — batch type `part`: exact-MPN search plus a minimal sexpr reader/writer that copies a stock KiCad symbol (flattening `extends`) into `Parts_emDashGameChanger` as pre-built `sym_text`, which `generate_library_files` uses instead of a template.
    - `DigikeyVoltageMap.py` — maps arbitrary voltage strings to Digikey's internal `ValueId`s for filtering (`parse_voltage_volts`, `lookup_value_id`).
    - `DigikeyPartNumber.py` — `check_api_response` (raises on 429/5xx so a quota fault shows as an API error, not "no results") and `pick_digikey_pn`, the shared rule every generator uses to choose which `ProductVariations` part number goes on the symbol: lowest minimum order quantity first, Cut Tape on a tie (so a reel-only number with a 60k MOQ never beats a Bulk or Cut Tape option).
    - `BatchImport.py` — batch-mode spec parser (`parse_batch_text`, `BatchSpec`), one resolver per type keyword in `BATCH_RESOLVERS`, and the runner (`run_batch`), independent of the GUI so it's testable/callable on its own. Transistor rows without a usable `pins=`/footprint come back as `needs_pinout` carrying their processed data; `plugin._on_api_result_batch` confirms them on the main thread and calls `record_generate`.
    - `tests/` — offline pytest suite (`python3 -m pytest tests`): batch parsing/resolution, `pins=` validation, the `needs_pinout` flow with stubbed search, package normalization against real Digi-Key strings, and on-disk existence of every stock footprint name.
    - `symbolTemplates/`, `footprintTemplates/` — Jinja2 templates `generate_library_files` renders into the final `.kicad_sym` / footprint output.
    - A generated `code_map.md` at the repo root has full file-by-file function/class listings if you need exact line numbers — regenerate it rather than trusting it as line numbers drift.

??? note "Decisions"
    - **Component = symbol + footprint + metadata, bundled.** A "component" isn't just a schematic symbol — it's generated together with its footprint, datasheet link, and ratings (voltage/power/tolerance/part number) so the user never has to separately hunt for a matching footprint. Part numbers on the generated symbol also mean BOM-plugin output can be uploaded straight back to Digikey for ordering.
    - **Shared per-category libraries, not one-file-per-part.** Generated parts are appended into existing `.kicad_sym` / `.pretty` libraries per category (e.g. all TH resistors → `R_TH_emDashGameChanger.kicad_sym`) rather than creating a new library file per component. Keeps the KiCad library list short and matches how users already organize libraries by category.
    - **Batch mode auto-picks cheapest in-stock match, no per-line picker.** The single-part GUI flow shows a results list to choose from; batch mode intentionally skips that and takes the cheapest in-stock hit automatically, since the point of batch mode is a non-interactive run over many lines. Report dialog afterward shows generated / already-existed / no-results / error per line so mistakes are still visible after the fact.
    - **Batch API calls run in parallel (`ThreadPoolExecutor`, `max_workers=5`).** Serial lookups were too slow for large batch files; 5 workers balances speed against Digikey rate limits. See `_search_job`/`run_batch` in `BatchImport.py`.
    - **Credentials live in a gitignored `config.json`, prompted for on first use.** `DIGIKEY_CLIENT_ID`/`DIGIKEY_CLIENT_SECRET` are never committed (`config.json` is in `.gitignore`); `CredentialsDialog` in `gui.py` collects them the first time the plugin runs and `plugin.py` persists them locally.
    - **`plugin.py` has a dual entry point.** It's a `pcbnew.ActionPlugin` when run inside KiCad, but stubs out `pcbnew` in a `try/except ImportError` at the top and has `if __name__ == "__main__": ... app.MainLoop()` at the bottom, so it can also run standalone (this is what the `~/.local/bin/kicadcompmaker` symlink + desktop launcher rely on). Same dual-import pattern (`from .gui import ...` vs `from gui import ...`) is used for the sibling modules so both the packaged-plugin and standalone-script cases resolve imports correctly.

    - **SMD parts only ever reference stock KiCad footprints.** No footprint generation for SMD; a package without a stock match sets `processed_data["error"]` and `generate_library_files` refuses it, rather than falling back to a near-miss footprint (e.g. a 3-pin SOT-23 diode, or a SOT-23-6 matched to a 3-pad footprint — `normalize_package_family` rejects pin suffixes above 3).
    - **HandSolder is a shared checkbox / `handsolder=` field, default on.** It flows through `lib_config["handsolder"]`. The symbol name doesn't encode it, so whichever variant is generated first wins dedup (documented in README).
    - **Transistor pinouts are never guessed into a library.** The SMD default pin numbers (SOT-23 BJT B1 E2 C3, MOSFET G1 S2 D3, JFET D1 S2 G3; tab packages differ) only pre-fill the confirm dialog. Batch uses `pins=` (validated as a permutation of the family's terminals); without it the row is deferred to the dialog after the batch rather than skipped or guessed.
    - **SMD transistors reuse the THT modules via an `smd` flag** instead of three more near-duplicate files.
    - **Batch picks the cheapest product that maps onto a stock footprint** (`_process_best`), not strictly the cheapest — MMBT3904's cheapest listing is a DFN variant with no stock footprint.
    - **Tantalum case picking:** manufacturer size code first, then the shortest stock Kemet body at least as tall as the part, else the standard full-height case.
    - **`_HS` suffix on hand-solder SMD symbols** so the hand-solder and standard variants of one part coexist; without it `append_to_lib`'s name dedup treats the second as already existing.
    - **Generic `part` type copies stock symbols rather than templating** — ICs/LEDs/trimmers vary too much for a template, and KiCad's stock symbol already has the right pins.
    - **Transistor search retries without parametric filters on a 400** and filters client-side — Digi-Key rejects filters for some exact MPNs ("Parametric Filtering Not Support at Parent Category Level", e.g. MMBFJ112).
